## 1. 架构概述与设计原则

系统采用**分层 + 横切关注点**的架构：上层前端 → 接入层 → Agent 编排层 → 能力服务层 → 数据存储层，训练/部署闭环位于底部，可观测性横切所有层。

设计原则：

1. **无状态可扩展**：后端服务不持有本地会话状态，会话由 Redis / PostgreSQL 承载，可水平扩缩。
2. **编排与能力分离**：LangGraph 负责编排（Agent 路由、状态流转），检索/记忆/LLM 作为可复用的能力服务。
3. **模型可替换**：统一 `LLMProvider` 抽象，DashScope / DeepSeek / 自训 vLLM 可无感切换。
4. **可信优先**：每个专业 Agent 输出必经合规风控 Agent 兜底，责任认定与法规检索必须有来源。
5. **真流式**：LLM 底层开启 `streaming=True`，经 contextvars/`asyncio.Queue` 管道逐 token 实时回传。
6. **容器化**：全部中间件与业务服务 Docker 化。

## 4. 分层详细设计

### 4.1 前端层

- SPA：Vue 3.5 `<script setup lang="ts">`，Pinia 状态，Router 守卫鉴权。
- 视图（7 个）：登录 / 智能对话（SSE）/ 运单审查（高亮联动）/ **货损责任认定（专属表单页）** / 知识检索（来源筛选）/ 审计日志 / 404。
- 构建：node:20 构建 → nginx 运行，`/api` 反代后端（`proxy_buffering off` 支持 SSE）。

### 4.2 接入层

- FastAPI 应用工厂（`app/main.py`），lifespan 初始化依赖。
- 组件：CORS、请求 ID 中间件、JWT 依赖注入、Redis 限流、`/healthz` 与 `/metrics`。
- 流式接口：`POST /api/v1/chat` 返回 `text/event-stream`，事件 `token` / `citations` / `done` / `error`。

### 4.3 Agent 编排层（LangGraph）

核心，详见第 5 节。

### 4.4 能力服务层

- `LLMProvider`（`app/llm/provider.py`）：封装 `ChatOpenAI(streaming=True)`，流式/非流式、超时、tenacity 重试、多模型缓存。
- `Embeddings`：`OpenAIEmbeddings(model=qwen3.7-text-embedding, dimensions=1024, chunk_size=10)`。
- 检索：`retrieval/milvus.py`（稠密 + BM25 稀疏混合检索）、`neo4j.py`（法条关系图）。
- 实体抽取：`retrieval/extraction.py`（规则优先，抽取 LAW/CONCEPT/CAUSE/COURT/MONEY/ORG/VEHICLE 实体与关系）。
- 工具：`search_statutes`、`search_cases`、`search_knowledge`、`parse_contract`（同步 Milvus/Neo4j 调用经 `run_in_executor` 放入线程池，避免阻塞事件循环）。

### 4.5 数据存储层

| 存储 | 用途 | 关键字段/索引 |
|---|---|---|
| MySQL 8 | 用户/会话/消息/文档/合同/审计 | 主键 + 外键 + 时间戳 |
| Milvus | 物流法律知识向量（1024 维稠密 + BM25 稀疏） | collection `legal_knowledge`，108 条向量 |
| Neo4j | 法条—案由—运输方式—判例关系图 | 191 节点 + 618 关系 |
| PostgreSQL 16 | LangGraph 检查点 + 长期记忆 | `checkpoints`/store 表 |
| Redis | 会话、限流、Celery broker | 令牌桶/滑动窗口 key |

## 5. 多 Agent 设计（LangGraph）

### 5.1 Agent 角色

| Agent | 职责 | 关键能力 |
|---|---|---|
| supervisor（主控） | 意图识别、任务路由、结果汇总 | 条件路由（6 类） |
| waybill_reviewer | 运单/运输合同条款级审查 | 规则扫描 + LLM 增强 + 风险分级 |
| statute_retrieval | 物流交通法规检索 | Milvus 稠密 + BM25 稀疏混合 + LLM 归纳 |
| case_retrieval | 物流交通判例检索 | Milvus 混合检索 + Neo4j 关系联想 + LLM 归纳 |
| liability_assessor | 货损货差责任认定 | 检索法条/判例 + LLM 综合研判 |
| document_writer | 物流法律文书草拟 | 检索法条 + 模板生成 |
| compliance_guard | 输出兜底安全审查 | 越权拦截、免责、脱敏、兜底生成 |

### 5.2 状态定义（AgentState）

`TypedDict`，核心字段：

- `messages`：对话累计（`add_messages` reducer）。
- `route`：supervisor 决策出的路由标签（waybill/statute/case/liability/document/chat）。
- `documents` / `citations`：检索到的文档与引用。
- `highlights`：运单审查高亮片段。
- `compliance_ok`：合规检查结果。
- `final_answer`：最终答复。

### 5.3 状态图与路由

```
START → supervisor ──┬─(waybill)    → waybill_reviewer ──────┐
                     ├─(statute)    → statute_retrieval ─────┤
                     ├─(case)       → case_retrieval ────────┤→ compliance_guard → END
                     ├─(liability)  → liability_assessor ────┤
                     ├─(document)   → document_writer ───────┤
                     └─(chat)       → (直连 compliance_guard)┘
```

`build_agent(llm, tools, checkpointer, store)` 编译时传入 `checkpointer=`（短期）与 `store=`（长期）。

> 路由优先级：document（起草/生成意图）优先于 liability（货损/赔偿关键词），避免「起草货损索赔函」被误路由到责任认定。

### 5.4 工具定义

| 工具 | 输入 | 输出 | 实现要点 |
|---|---|---|---|
| `search_statutes` | 查询词 | 法规/条文 + 法条号 + 领域 + 分数 | Milvus 混合检索，`meta["source_type"]=="statute"` 过滤 |
| `search_cases` | 案情描述 | 判例 + 适用法条 + 关系 | Milvus 混合检索（`source_type=="case"`）+ Neo4j 图联想 |
| `search_knowledge` | 查询词 | 通用知识向量命中（保留真实来源类型） | Milvus 稠密检索 |
| `parse_contract` | 文本/文件 | 结构化条款列表 | python-docx / pdfplumber（线程池） |

## 6. 流式输出架构（真流式）

这是本系统体验的关键，实现「逐 token 实时回传」而非「等完整结果一次性返回」。

### 6.1 组件

| 组件 | 文件 | 职责 |
|---|---|---|
| token 管道 | `app/agents/streaming.py` | contextvars 存 `asyncio.Queue[str]`，提供 `start_streaming`/`stop_streaming`/`emit_token` |
| 流式编排 | `app/services/chat.py` | 后台跑 graph + 前台消费 token 队列实时 yield |
| 底层流式 | `app/llm/provider.py` | `ChatOpenAI(streaming=True)`，`astream` 真流式 |
| SSE 端点 | `app/api/chat.py` | 逐事件回传 `token`/`citations`/`done`/`error` |

### 6.2 数据流

```
stream_chat 启动:
  1. start_streaming() 建队列，写入 contextvar
  2. 后台 task 跑 agent.astream(stream_mode="updates")
  3. 生成节点内 llm.astream(...) 逐 chunk emit_token(token) 推队列
  4. 主循环 queue.get(timeout=0.1) 拿到 token 立即 yield

结束:
  5. 排空剩余 token → yield citations → yield done
  6. 非流式路径（waybill）通过 streamed 标志补发 final_answer
```

### 6.3 关键点

- **contextvars 传递**：后台 task 通过 copy_context 继承 `start_streaming` 写入的队列，节点内 `emit_token` 能拿到队列。
- **必须 `streaming=True`**：若底层未开启，`astream` 会先一次性 `ainvoke` 完再切块，导致前端一直转圈（已修复）。
- **SSE 事件格式**：`event: token` + `data: {"content":"..."}`，末尾 `event: citations` + `event: done`。

## 7. 记忆架构

- **短期记忆**：`langgraph.checkpoint.postgres.PostgresSaver`，保存会话检查点，支持中断恢复与多轮上下文。
- **长期记忆**：`langgraph.store.postgres.PostgresStore`，保存跨会话语义记忆（用户画像、案件历史）。
- 连接：两者复用 `DB_URI`（PostgreSQL）。MySQL 业务库走独立的 async aiomysql，两库彻底分离。

## 8. 检索架构与物流法律知识库

### 8.1 知识库构成

知识库覆盖公路货运、快递寄递、铁路运输、航空运输、水运海商、仓储、多式联运、危险货物运输、冷链、货运代理、超限超载等全领域。当前入库规模：

| 类型 | 数量 | 说明 |
|---|---|---|
| 法规条文 | 56 条 | 覆盖 8+ 部法律 |
| 判例 | 32 条 | 7+ 个案由（公路货运/快递/海商/铁路/航空/多式联运/冷链/货代） |
| 概念 | 20 条 | 物流法律术语 |

数据来源包括：

| 来源 | 关键内容 |
|---|---|
| 《民法典》运输合同章 | 第 809-842 条，承运人/托运人/收货人权利义务、货损赔偿、多式联运 |
| 《道路运输条例》(2023) | 货运经营许可、危险货物运输资质、承运人责任险、超限超载 |
| 《快递暂行条例》(2025) | 快件损失赔偿、保价规则、验视义务、用户信息保护 |
| 《邮政法》 | 给据邮件赔偿、免责事由 |
| 《海商法》(2025) | 海上货物运输合同、承运人责任期间、适航/管货义务 |
| 《铁路法》 | 货物运输赔偿、保价运输、免责 |
| 《民用航空法》(2026) | 航空货物运输责任、延误、赔偿限额 |
| 《危险货物道路运输安全管理办法》 | 危险货物托运/承运资质、挂靠禁止、押运 |

### 8.2 混合检索策略（均在 Milvus 内完成）

1. 关键词精确：BM25 稀疏向量（法条号、精确术语，jieba 分词）。
2. 语义召回：query → `qwen3.7-text-embedding`（1024 维稠密向量）→ Milvus 相似检索。
3. RRF 融合：`RRFRanker(k=60)` 融合稠密 + 稀疏召回，兼顾语义与关键词。
4. 关系联想：Neo4j 法条/案由/运输方式/判例图，做类案与法条关联。
5. **来源过滤**：`search_statutes`/`search_cases` 通过 `meta["source_type"]` 分区检索，避免法条被判例污染。

### 8.3 知识入库管道

`generate_rag_data.py` 产出结构化语料（法条/判例/概念 JSONL + 图节点关系），
`ingest_milvus.py` / `ingest_neo4j.py` 分别入库向量库与图库；增量文档经 Celery 异步解析入库。

## 9. 模型训练与部署架构

```
数据工程 → PT(继续预训练) → SFT(监督微调) → DPO(偏好对齐) → 评估门禁 → vLLM 部署
                                                          ↑ 不达标回炉 ──┘
```

| 阶段 | 目标 | 超参（默认） |
|---|---|---|
| PT | 注入物流交通法律领域知识 | lr=2e-5, epochs=1, LoRA |
| SFT | 指令/对话/工具调用对齐 | lr=2e-4, epochs=3, LoRA |
| DPO | 安全与效果偏好对齐 | lr=5e-5, beta=0.1 |
| 评估 | 自动指标 + LLM Judge + 红队 | 全过才发版 |
| 部署 | 高吞吐推理 | vLLM + GPTQ/AWQ 量化，灰度 A/B |

LoRA 统一：r=16、alpha=16、dropout=0，目标模块 `q/k/v/o_proj + gate/up/down_proj`。基座 Qwen2.5-7B / Qwen3-8B。

训练产物 → merge → `/models/merged/{version}` → `vllm serve`；生产经 `LLMProvider` 切换自训 vLLM 或 DashScope。

## 10. 安全架构

- **接入安全**：JWT + bcrypt、RBAC、OIDC/Keycloak SSO 扩展。
- **账号治理**：首次启动种子默认管理员（`ADMIN_*` 可覆盖），开放 `/auth/register` 注册普通用户。
- **内容安全**：合规风控 Agent 兜底（越权结论拦截、免责声明）、敏感词库、prompt 注入防护。
- **数据安全**：PII 脱敏（手机号/身份证/银行卡/邮箱）、文件加密存储、传输 TLS、日志脱敏。
- **防滥用**：Redis 令牌桶/滑动窗口限流、LLM 失败熔断与重试。
- **审计**：所有 LLM 调用、检索、导出落审计日志。
